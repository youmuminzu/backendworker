## backendworker 首次实跑排错（用户本地跑 --init-ddl + 全量导入）

**故障 1：建表 400 Bad Request**
- 根因：`tables.sql` 文件头用 `#` 注释，`#` 不是 SQL 注释，`_split_ddl()` 只剔 `--` 开头行，
  文件头被拼进首条 CREATE TABLE → D1 400。wrangler `--file` 同样会因此报错。
- 修：`_split_ddl()` 同时剔 `--` 与 `#` 整行，并校验每条片段必须以 CREATE/DROP/ALTER/PRAGMA 开头；
  `run_ddl` 逐条打印 `DDL [i/n] ...`，失败时带出错语句。
- 修：`_post()` 之前把 400/401/403 也当可重试（raise_for_status 抛 HTTPError 被统一 catch），
  白重试 5 次且丢掉 D1 body。改为：仅网络异常 + RETRYABLE_STATUS 退避重试，
  其余 4xx 立即抛 `D1Error` 并附响应体。
- 修：jieba 导入刷屏 SyntaxWarning（源码非法转义），在 `tokenizer.initialize()` 用 catch_warnings 静默。

**故障 2：7 个站点 FOREIGN KEY constraint failed（beijing/fujian 成功）**
- 根因：`product.category_id` 声明了 `REFERENCES category(category_id)`，但该列是 `||` 拼接的
  **多值列**，SQLite 外键比整个字段值 → 多值必然失败。实测各站点多值行数：
  beifang 394 / guangdong 7914 / guiyang 1043 / hainan 886 / hangzhou 830 / shanghai 5115 / zhengzhou 377；
  beijing、fujian 多值行数为 0，故唯二成功。
- DESIGN.md §7 原判断「D1 外键不校验 || 拼接串内部」是**错的**，已更正。
- 修：product.category_id 去掉外键（market_id 单值保留外键）。SQLite/D1 无法删列约束，必须整表重建。

## 去掉 UNIQUE 约束与 category 索引（用户依据 D1 控制台实测提出）

- 背景：D1「使用情况」的**已写入行数包含索引写入**，索引会让写入行数被重复计算。
- 改动：`product` 表去掉 `UNIQUE (market_id, raw_data_key)`、去掉 `idx_product_category`；
  只保留 `idx_product_market`（导入端每批回查 `WHERE market_id=? AND raw_data_key IN (...)` 依赖它，
  去掉会全表扫描）。分类检索走 `product_fts.category_id` 全文索引。
- **连带必须改的代码**：没有 UNIQUE 约束就不能用 `ON CONFLICT(market_id, raw_data_key) DO UPDATE`
  （SQLite 报 does not match any PRIMARY KEY or UNIQUE constraint）。
  `product_sync._apply_added` 改为「先查存在性」：不存在的走纯 INSERT、已存在的走 UPDATE
  （`_update_sql` 已抽成静态方法，与 `_apply_changed` 复用）。

**重要性能坑（去掉复合索引后必踩）**：唯一约束没了，`WHERE market_id=? AND raw_data_key IN (...)`
只剩单列 `idx_product_market`，会退化成「扫该站点已入库全部行」。逐批回查会让全量读取涨到约 260 万行。

**最终方案（用户拍板）：全程零回查，不做任何存在性校验。**
用户明确要求：insert/update 都不做 (market_id, raw_data_key) 唯一验证，省掉所有查询；
实际跑出少量重复他另写脚本处理。实现要点：
- 新增：product 的 INSERT 与对应 FTS 的 INSERT **相邻放同一批脚本**，FTS 用 `last_insert_rowid()`
  取 rowid（D1 的 RETURNING 在部分构建上不可用，不能用）。
  `product_sync._chunk_pairs()` 保证这一对永不被拆到两个请求；
  `D1Client.multi_statement_enabled` 为 False（已降级逐语句）时 `_apply_added` 直接抛错中止，
  避免写坏索引。
- 变更/下架：rowid 用子查询 `SELECT product_id FROM product WHERE ...` 就地取，无额外 HTTP 往返。
- 删除 `_load_market_map` / `self._ids` / `_fetch_ids` / `_write_fts` / fresh-stale 分流。
- 新增路径读取量：260 万 → **0**。
- 不提供改表逻辑，用户手动改表。

## product 表新增 update_at 字段（用户要求）

- `tables.sql`：product 加 `update_at TEXT`，存本行最后一次插入/更新的时间
  （格式 YYYY-MM-DD HH:MM:SS，复用 `state.now_str()`）。
- `product_sync.py`：新增常量 `DERIVED_COLUMN = "update_at"`；
  `_insert_sql()` 的列清单里带上它并写入当前时间，`_update_sql()` 的 SET 里追加刷新。
- 关键：**不参与 diff 比较** —— COMPARE_FIELDS 由 CSV 列名 FIELDS 派生，
  update_at 不在其中，所以不会被误判为「变更」触发无谓 UPDATE。
- 字段名按用户原话用 `update_at`（注意：项目里 market.json / product_files.json 用的是 `updated_at`，
  两边不一致，若用户后来想统一成一个名字，改 DERIVED_COLUMN + tables.sql 两处即可）。

## GitHub Actions 定时部署（每天北京时间 03:00）

- 新增 `.github/workflows/import.yml`：cron `0 19 * * *`（UTC，= 北京时间次日 03:00）。
- **最大的坑（已在 workflow 里解决）**：CI runner 每次全新环境，而 `_old.csv` 是 diff 基准。
  不持久化 → 每轮全量判成「新增」→ 重复入库；product 表已无 UNIQUE 约束，**重复不会报错只会静默堆积**。
  所以流程做成「aws s3 sync 从 R2 拉 processeddata → 跑导入 → 再把 *_old.csv 回传 R2」。
  sync_state 在 D1 里天然跨轮保留。
- 用 aws CLI（ubuntu runner 自带）走 R2 的 S3 API，Storage 仍为 LocalStorage，`R2Storage` 留作可选演进。
- job 级 concurrency group + cancel-in-progress: false（排队而非打断，避免并发写库）。
- workflow_dispatch 支持勾选 --init-ddl / --rebuild-stats；日志 tee 到 import.log，
  写入 $GITHUB_STEP_SUMMARY 并上传 artifact。
- 需要的 Secrets：CLOUDFLARE_API_TOKEN / _ACCOUNT_ID / _D1_DATABASE_ID /
  R2_ACCESS_KEY_ID / R2_SECRET_ACCESS_KEY / R2_BUCKET / R2_ENDPOINT_URL。
- 用 `uv sync` 而非 `--frozen`，避免 uv.lock 与 pyproject 不同步时 CI 直接失败。

**用户纠正（重要）**：我原先认为 CI 必须把 `_old.csv` 下载/上传回传，这是错的。
用户的架构是：**Storage 抽象的意义就在于 CSV 读写全走 R2**，本地 LocalStorage 只是为了方便调试
而临时替代；生产环境下 `_new.csv → _old.csv` 的改名直接发生在 R2 里。
所以 runner 不需要任何本地快照，**拉取/回传步骤纯属多余，已删除**。

## 实现 R2Storage（storage.py）

- 基于 boto3 的 S3 兼容 API（pyproject 加 boto3 依赖）。

  （bucket / endpoint / keys / ACCOUNT_ID 统一用正则解析，CI 无该文件走环境变量）。
